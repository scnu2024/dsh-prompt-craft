# 本轮真实评测结果

结论：**收益尚未证实。候选策略未通过独立验收，保持默认关闭。** 日常一键打磨继续使用现有策略，不启动答案生成或评审。

2026-11-08 在本地 DSH 宿主完成真实模型调用。题集共 30 个手写合成任务，10 个开发任务，20 个独立验收任务。验收每题两轮，共 40 对、80 份答案。两版都使用 `deepseek-account/deepseek-flash`、`low`、4000 tokens 上限、相同材料和无工具环境。打磨实际使用 `off`，每题最多两次调用。代码由隔离子进程执行预先固定的测试，分析答案采用匿名交换顺序复判。

开发阶段最后一轮原提示词代码题通过 5/6，旧插件基线 6/6，候选 6/6；共 62 次调用、约 72 秒。这一小样本优势未在独立验收中复现。更早两轮有效开发试验的候选均为 5/6；最早一次宿主缓存旧模块的试跑已标记无效，未纳入结论。最后开发轮之后仅整理语言、接口约束及简单概念识别规则，随后冻结验收快照；验收中途没有调整策略。

## 逐例差异和退步原因

1. `accept-impl-group` 第二轮：原答案使用 `key if callable(key) else (lambda record: record[key])`，候选使用 `value = key(record)`，输入字符串字段名时出现 `'str' object is not callable`。第一轮原答案也在同一题失败。题目对 key 的类型说明不足，结论保留这一局限，两个版本均按预先固定的字符串字段名测试评分，未事后修改或删除题目。
2. `accept-control-status` 两轮：原请求为“用一句话解释 HTTP 403，不提供解决方案”。候选追加了“按现象、证据与原因的关联进行解释”等流程。原答案直接说明服务器理解请求但拒绝授权；候选第一轮延伸到“需结合响应体或服务器日志判断”，第二轮也明显冗长。简短请求受到过度流程影响。
3. `accept-analysis-cache`：候选把已给出的缓存命中证据写成仍需确认的推测，增加了重复的证据分类。匿名评审交换顺序后结论冲突，记为不确定。
4. `accept-control-closure`：打磨返回原文“什么是闭包？”，两轮回答仍有措辞差异，其中一轮被判候选胜出。这说明生成随机性会影响小样本胜负，单次漂亮答案不能证明改写有效。

## 评测器修正与完整性说明

原始统计中候选为 24/28。审阅发现 `accept-impl-diff` 两轮候选返回列表内的元组，题目只要求剩余区间，没有要求内部必须使用列表。早期 Python 评测器使用 Python 严格序列比较，造成两个有效答案误判。现改为与 JavaScript 相同的 JSON 结果归一化，并补充自动测试。

使用已保存的全部代码答案重放，未调用模型、未修改提示词、答案、样例或预期值。仅上述两条检查发生变化，候选修正为 26/28。原始报告完整保留，修正报告记录原始 SHA256、原始统计及每一项变化。

80 份最终答案与匿名评审结果均已保存。本次两次输出截断的评审只保存了失败原因和输出长度，没有保存截断文本；首轮评测基础设施存在这一审计缺口。后续入口已经补齐逐块记录输入、输出和结束状态，包括修复调用与中断前的部分文本。本轮没有补造缺失内容，也没有为获得更好结果重跑验收。
