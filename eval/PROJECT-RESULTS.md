## 具体答案与失败案例

- `project-accept-callbacks` 第二轮：冻结基线答案捕获 record，原 records 改变后 job 的 id 也改变，预写测试失败；原提示词和候选捕获创建时的 id，均通过。候选返回了原提示词，这一分差不能单独证明改写策略有效。
- `project-accept-plan` 第二轮：候选返回原文，回答仍额外推测统计信息、回表成本和选择率。与生产基线的两次匿名比较一致标记其违反“只基于这些证据”。此条说明回答模型自身会违反清晰限制，不能把原文保留理解为答案质量保证。
- `project-accept-ownership` 第一轮：候选保留了只解释、不修改代码，但回答又追加“修复方向”和解绑建议，匿名比较标记越界。与原提示词的首次评审达到输出上限，整组保留为不确定；与生产基线的两次评审均判基线更符合要求。
- HTTP 403 对照返回原文，没有追加证据分类、查日志或解决步骤。实际 DSH 中的“再短一点”和“再具体一点”也保留了原来的简短要求。

全部 120 份回答成功返回。一次分析评审达到输出上限，记录终止原因和已接收文本，保留在统计中；该次没有收到文本输出。没有为了改善结论重跑、剔除失败题、修改验收题或调低门槛。

两个开发轮的代码题均为三个版本各 7/7，未显示优势。第一轮后仅修正了一句话请求快速返回的识别；第二轮冻结后进行独立验收。实际界面测试期间补充的客户端提示字段、顶部取消修复，以及损坏修复输出的错误处理均另行自动验证，没有用来重写冻结验收输出。新增执行策略最终保持关闭。

## 原因修复与交付行为

移除模型输出后的固定流程追加，纠正否定句和组合任务识别，统一可见用户材料的事实来源，增加限制丢失和明显冲突检查。确认回答、附件名和实际提供的用户历史可作为依据；历史助手假设不能成为已确认事实。修复最多使用剩余一次调用，仍不安全则保留原文；网络、超时及损坏 JSON 保持可见错误和已有候选。结果增加中英文原文保留提示。

实机还发现生成时顶部“取消”实际清除结果，底部取消才恢复旧候选。已统一两者，并补充两个入口的回归测试。详情和复跑说明见 [README.md](README.md)。
